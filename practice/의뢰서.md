## 0단계 (2026-08-05 추가, 다른 항목들보다 먼저 다뤄야 함) — 들여쓰기 = 블록 소속

**계기**: `api-server/server.py`의 `handle_client()` 타이핑 중, `finally:` 블록 안의 `if state.session_id is not None...`(8칸)을 보고 사용자가 "이거 pong 응답 신호 정리하는 거야?"라고 물음 — 완전히 다른 위치(`while` 반복문 안)에 있는, 전혀 다른 목적의 `if payload.get("type")=="pong":`과 헷갈린 것. **원인: `if`라는 키워드가 같아서 같은 것으로 인식** — 들여쓰기 칸수나 코드가 물리적으로 몇 번째 줄인지가 아니라, "이 줄이 지금 어떤 블록(함수/if/for/try/finally) **안**에 있는가"를 봐야 하는데, 그 판단 기준 자체가 아직 안 서 있는 상태. [[user_background]]에도 "들여쓰기를 옆 줄과 시각적으로 맞추는 습관" 관련 기록 있음 — 근본 원인이 같음.
- **진짜 배워야 하는 것**: 코드를 볼 때 "이름이 같은 키워드(`if`, `for`)"가 아니라 "이 줄을 감싸고 있는 블록이 뭔지"를 먼저 확인하는 습관. 비유: 같은 "출입문"이라는 단어라도 어느 건물 문인지에 따라 완전히 다른 곳으로 들어가는 것과 같음.
- **연습 아이디어**: 일부러 `if`문 2~3개를 서로 다른 함수/블록 안에 흩어놓은 짧은 예제를 만들어서, "이 줄은 어떤 블록 안에 있게요?"를 먼저 맞혀보게 하고, 그다음 실제로 코드를 실행해서 확인하는 방식. 지금 겪은 실제 사례(pong if vs session 정리 if)를 그대로 축소한 예제로 써도 좋음 — 실제로 헷갈렸던 것이라 체감이 큼.
- 다른 연습(1~6번)보다 **먼저** 다뤄야 함 — 저 항목들도 결국 `if`/`for`/`try` 블록 구조 위에서 벌어지는 일이라, 블록 소속 판단이 안 되면 계속 같은 방식으로 헷갈릴 가능성 높음.

## 0-2단계 (2026-08-05 추가) — 한 줄짜리 복잡한 조건문을 "읽는 순서"

**계기**: `handle_client()`의 `finally` 블록에서 `if state.session_id is not None and sessions.get(state.session_id) is writer:` 줄을 다루면서, 사용자가 본인의 읽는 방식을 스스로 밝힘 — **"무작정 오른쪽 괄호에서 시작해서 왼쪽으로 넘어간다"**. 이건 사칙연산에서 "괄호부터 계산"이라는 규칙을 가져와 기계적으로 적용한 것으로 추정되지만, 이런 조건문에는 안 맞는 방식.

- **왜 안 맞는지**: 이 줄은 사실 `and`로 이어진 **두 개의 독립된 질문**입니다.
  1. `state.session_id is not None` (질문 A: session_id가 있나?)
  2. `sessions.get(state.session_id) is writer` (질문 B: 그 session_id가 지금도 나를 가리키나?)
  - `and`는 "A와 B **둘 다** 참일 때만 전체가 참"이라는 뜻. 오른쪽 괄호부터 거꾸로 읽는 게 아니라, **왼쪽부터 순서대로 A를 통째로 판단 → `and` 만나면 B를 통째로 판단 → 둘을 합침**이 맞는 순서.
  - 각 질문(A, B) *안에서*는 함수 호출(`sessions.get(...)`)이 있으면 그 안쪽(괄호 안)을 먼저 계산하는 게 맞지만, 이건 "그 질문 하나를 계산할 때의 순서"일 뿐 — 줄 전체를 오른쪽에서 왼쪽으로 훑는 것과는 다른 이야기.
- **비유 후보**: 문장을 읽을 때 "그리고"로 연결된 두 문장("밥을 먹었고, 설거지를 했다")을 오른쪽 문장부터 거꾸로 읽지 않는 것처럼, `and`로 이어진 조건도 왼쪽 조건부터 순서대로 읽는 게 자연스러움 — 그 비유로 교정 시도.
- **연습 아이디어**: `and`/`or`로 이어진 조건문을 몇 개 만들어서, 각 부분(A, B)이 각각 참/거짓인 예시 값을 주고 "전체 결과가 뭘까?"를 미리 예측해보게 한 다음 `print`로 실제 확인. 함수 호출이 섞인 조건(`.get()` 등)도 하나 포함해서, "괄호 안쪽 계산"과 "줄 전체를 읽는 방향"이 다른 문제라는 걸 구분시킬 것.
- 위 0단계(블록 소속)와 이어지는 문제 — 둘 다 "코드를 왼쪽→오른쪽, 위→아래로 순서대로 읽지 않고 시각적 패턴으로 처리하려는 습관"에서 나온 것으로 보임. 두 개를 묶어서 "코드는 사람 말처럼 순서대로 읽는 것"이라는 큰 원칙 하나로 같이 가르치는 게 효율적일 수 있음.
- **(2026-08-05, 사용자 본인 평가)** 사용자가 스스로 "별 발전이 없고 계속 잘못 이해하는 것 같다"고 밝힘. 연습 진행 시 이걸 고려할 것 — 여러 세부 개념을 한 번에 늘어놓기보다, **0단계(블록 소속)/0-2단계(읽는 순서) 같은 "가장 기초적인 코드 읽기 습관"부터 먼저 확실히 다지고**, 그 다음에야 동시성 등 상위 개념으로 넘어가는 순서가 맞을 가능성이 큼. 진도 압박보다 "실제로 스스로 설명할 수 있는가"를 기준으로 삼을 것 — 이해 안 된 상태로 다음 개념 쌓지 말 것.

## 다룰 개념 (전부 이미 `client` 코드 만들면서 한 번씩 배웠지만, 다시 헷갈렸던 것들)

1. `create_task`/`async`가 실제로 "동시에" 도는 것 — `print`+`asyncio.sleep`으로 눈에 보이게 확인
2. `json.loads`/`dict.get()`으로 데이터 꺼내기
3. `if`/`continue`로 조건에 따라 흐름 건너뛰기
4. `try`/`except`/`finally`로 에러 나든 안 나든 원하는 부분 실행하기
5. **`done, pending = await asyncio.wait(...)` 튜플 언패킹** — `done`/`pending`은 dict가 아니라 set(집합)이라는 것. 2026-08-04에 이 부분에서 실제로 헷갈렸음(`-> dict` 반환타입 힌트와 `done`/`pending`을 혼동함) — 꼭 짚고 넘어갈 것.
6. **왈러스 연산자(`:=`)와 `while line := await reader.readline():` 패턴** (2026-08-05, `api-server/server.py`의 `handle_client()` 타이핑 중 헷갈려서 추가됨) — "읽으면서 동시에 변수에 담고, 그 값으로 반복 조건도 검사"하는 3단 동작이 한 줄에 뭉쳐 있어 낯설어함. 공백 없이 붙여 써야 하는 한 토큰(`:=`)이라는 점도 오타 유발 지점이라 같이 짚을 것.

## 진행 방식 규칙 (`~/myrag/의뢰서.md`와 동일 — 반드시 지킬 것)

1. **코드는 절대 대신 써주지 않기.** Write/Edit로 파일을 만들지 않음 — 사용자가 터미널 `nano`로 직접 타이핑. AI는 설명 + 타이핑 후 결과 확인(읽어서 검증)만.
2. **아주 작은 단위로.** 한 번에 2~5줄씩만, 타이핑 후 바로 확인하고 다음 단계로.
3. **영어 단어는 항상 쉬운 한글 뜻 병기.** 사용자가 "영어 단어에 까막눈"이라고 명시함 — 코드 로직 설명과 별개로, 이름에 쓰인 영어 단어 자체의 뜻도 매번 짚어줄 것 (예: `ticker` = "똑딱거리는 것"이라는 뜻). 이전에 이미 설명한 단어라도 생략하지 말고 매번 다시 넣을 것.
4. **이해했는지 명확히 판정.** 본인 말로 설명해보라고 하고, 맞으면 "맞습니다", 틀렸으면 정확히 어디가 틀렸는지 짚어줄 것.
5. **비유 적극 활용.** 이미 통했던 비유 재사용: 라면 끓이기(비동기), 요리 중 불나면 소화기(try/except), 가스불 끄기(finally).
6. **터미널만 사용**, `nano`로 편집.
7. 매 파트 끝날 때마다 `~/myrag/타임테이블.md`에도 진행 상황 기록 (이 연습도 타임테이블에 진행 기록 남길 것 — 별도 파일이지만 같은 프로젝트 기록에 통합).

## 제안하는 진행 순서 (참고용 — AI가 상황 봐서 조정 가능)

1. `print_ticker()`: 1초 간격으로 "틱 0/1/2" 출력하는 짧은 함수
2. 다른 함수(`slow_task()` 등) 하나 더 만들어서, `asyncio.create_task`로 둘을 동시에 돌려 "진짜 동시에 실행되는 것"을 눈으로 확인
